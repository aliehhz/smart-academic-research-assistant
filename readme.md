# دستیار پژوهشی آکادمیک هوشمند

**تاریخ:** ۱ آذر ۱۴۰۵  
**وضعیت پروژه:** در حال توسعه (Work in Progress)  
**نام مخزن:** `smart-academic-research-assistant`  
**زبان پیاده‌سازی:** Python  
**نسخه پیشنهادی Python:** 3.10 یا بالاتر

دستیار پژوهشی آکادمیک هوشمند یک پروژه پایتونی برای کار با مقاله‌های پژوهشی است. این پروژه مسیر پاسخ‌گویی مبتنی بر **بازیابی متن (RAG)** را از مسیر **خلاصه‌سازی کل سند** جدا می‌کند.

هدف پروژه، فراهم‌کردن بستری ماژولار برای پرسش‌وپاسخ درباره محتوای مقاله و تولید خلاصه‌ای متکی بر متن منبع است.

> **هشدار وضعیت:** این مخزن نسخه‌ای اولیه و در حال تکمیل است. ساختار و رفتار بعضی بخش‌ها هنوز تغییر می‌کند؛ بنابراین نباید آن را محصول نهایی یا سامانه‌ای کاملاً ارزیابی‌شده در نظر گرفت.

## قابلیت‌ها و معماری فعلی

ساختار پروژه به ماژول‌های جداگانه تقسیم شده است تا پردازش فایل، بازیابی اطلاعات و تولید پاسخ مستقل‌تر توسعه یابند. بر اساس اجزای فعلی پروژه، ماژول‌های زیر در نظر گرفته شده‌اند:

- **ورود و پردازش سند:** `pdf_reader.py` برای خواندن PDF و `ingest.py` برای آماده‌سازی ورودی‌ها.
- **تقسیم متن:** `chunker.py` برای تبدیل متن سند به بخش‌های کوچک‌تر و مناسب بازیابی.
- **نمایه‌سازی برداری:** `vector_store.py` و پوشه محلی `chroma_db/` برای نگه‌داری و بازیابی داده‌های برداری.
- **پرسش‌وپاسخ مبتنی بر بازیابی:** `rag_chain.py` برای بازیابی قطعه‌های مرتبط و ساخت پاسخ بر اساس زمینه بازیابی‌شده.
- **خلاصه‌سازی سند:** `summarizer.py` برای مسیر خلاصه‌سازی که از پرسش‌وپاسخ مبتنی بر چند قطعه متمایز است.
- **هدایت درخواست:** `router.py` و `main.py` برای تشخیص مسیر مناسب و اجرای برنامه.
- **ارتباط با مدل زبانی و تنظیمات:** `llm_service.py` و `config.py` برای بخش‌های مرتبط با مدل و پیکربندی.

جزئیات دقیق رفتار هر ماژول به نسخه کد وابسته است. این README هم‌زمان با پیشرفت پیاده‌سازی به‌روزرسانی خواهد شد.

## پیش‌نیازها و راه‌اندازی

### پیش‌نیازها

برای اجرای پروژه به موارد زیر نیاز دارید:

- Python نسخه 3.10 یا بالاتر؛
- Git؛
- وابستگی‌های ثبت‌شده در `requirements.txt`؛
- دسترسی شبکه و یک کلید معتبر API، در صورتی که مسیر تولید پاسخ از Gemini استفاده کند.

برای راهنمای رسمی راه‌اندازی Gemini API و SDK پایتون، به مستندات [Google AI for Developers — Gemini API](#منابع) مراجعه کنید.

### راه‌اندازی در ویندوز

در PowerShell ویندوز، پس از دریافت مخزن، دستورات زیر را از پوشه اصلی پروژه اجرا کنید:

```powershell
git clone https://github.com/USERNAME/smart-academic-research-assistant.git
cd smart-academic-research-assistant
py -3.10 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

اگر اجرای اسکریپت‌های PowerShell مسدود است، سیاست اجرای سیستم را مطابق سیاست‌های امنیتی سازمان یا رایانه خود بررسی کنید. تغییر این سیاست باید آگاهانه انجام شود.

### راه‌اندازی در لینوکس و macOS

در لینوکس یا macOS، ساخت و فعال‌سازی محیط مجازی به شکل زیر است:

```bash
git clone https://github.com/USERNAME/smart-academic-research-assistant.git
cd smart-academic-research-assistant
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

> **نکته درباره نشانی مخزن:** مقدار `USERNAME` یک جای‌نگهدار است. آن را با نام کاربری GitHub واقعی و نشانی نهایی مخزن جایگزین کنید. اگر پروژه در سازمان یا مخزن دیگری قرار دارد، کل URL را مطابق نشانی واقعی تغییر دهید.

### پیکربندی و اجرای برنامه

پیش از اجرا، شیوه تنظیم کلید و نام متغیرهای محیطی را با `config.py` و مستندات همان نسخه از پروژه تطبیق دهید. نام متغیر مشخصی در این README حدس زده نشده است، زیرا ممکن است در نسخه‌های در حال توسعه تغییر کند.

کلید Gemini را در کد، فایل‌های commit‌شده یا مخزن عمومی قرار ندهید. کلید را در متغیر محیطی یا سازوکار امن مورد انتظار همان نسخه تنظیم کنید.

پس از تنظیم پیکربندی، نقطه شروع فعلی پروژه `main.py` است:

```bash
python main.py
```

ممکن است لازم باشد PDF ورودی را در مسیری قرار دهید که کد انتظار دارد. چون مسیر ورودی و رابط خط فرمان در نسخه‌های در حال توسعه تغییرپذیرند، برای جزئیات عملیاتی به `config.py` و `main.py` همان نسخه مراجعه کنید.

## نحوه استفاده و ملاحظات پاسخ‌گویی

در طرح فعلی، درخواست‌ها باید بر اساس نوع خود به مسیر مناسب هدایت شوند:

- **پرسش درباره یک موضوع یا بخش مشخص از مقاله:** از مسیر RAG استفاده می‌شود. سیستم قطعه‌های مرتبط را بازیابی می‌کند و پاسخ را با اتکا به همان زمینه می‌سازد.
- **درخواست خلاصه کل مقاله:** باید به مسیر خلاصه‌سازی سند هدایت شود. بازیابی چند قطعه به‌تنهایی معادل خواندن و خلاصه‌کردن کل متن نیست.

این تفکیک برای کاهش پاسخ‌های ناقص یا نامستند اهمیت دارد. اگر متن بازیابی‌شده برای پاسخ کافی نباشد، سامانه باید این محدودیت را آشکار کند، نه اینکه جزئیات مقاله را حدس بزند.

### تفاوت RAG و خلاصه‌سازی کل سند

در RAG، فقط بخش‌هایی از سند که برای پرسش مرتبط تشخیص داده می‌شوند بازیابی و در اختیار مدل قرار می‌گیرند. این مسیر برای پرسش‌های محدود و موضوعی مناسب است، اما ممکن است همه اطلاعات لازم برای یک جمع‌بندی جامع را در بر نداشته باشد.

در خلاصه‌سازی کل سند، هدف بررسی متن کامل استخراج‌شده و تولید جمع‌بندی از کلیت مقاله است. بنابراین، اجرای مسیر RAG با چند قطعه پراکنده نباید به‌عنوان جایگزین خلاصه‌سازی کامل سند در نظر گرفته شود.

با این حال، تشخیص نیت و انتخاب مسیر در نسخه فعلی هنوز به آزمون و بهبود نیاز دارد. برای نمونه، عبارت‌های کامل درخواست خلاصه ممکن است همیشه درست تشخیص داده نشوند.

پاسخ مدل را با متن اصلی مقاله بررسی کنید، به‌ویژه برای استفاده دانشگاهی یا استناد علمی. این پروژه جایگزین بررسی منبع اولیه نیست.

## وضعیت توسعه و مسیر پیش‌رو

پروژه فعلاً در حال تکمیل است و هنوز نسخه پایدار یا انتشار رسمی ندارد. قابلیت‌ها، رابط اجرا و تنظیمات ممکن است تغییر کنند؛ بنابراین این مخزن را نمونه کار و بستر توسعه بدانید، نه نرم‌افزار آماده استفاده پژوهشی بدون بازبینی.

محورهای پیشنهادی برای ادامه توسعه عبارت‌اند از:

- بهبود تشخیص نیت برای تفکیک مطمئن خلاصه‌سازی، پرسش‌وپاسخ و درخواست‌های مبهم؛
- اجرای تشخیص نیت محلی و سبک برای کاهش وابستگی این مرحله به سرویس آنلاین؛
- تکمیل مسیر خلاصه‌سازی کل سند، از جمله دسترسی پایدار به متن کامل استخراج‌شده؛
- افزودن آزمون‌های خودکار برای پردازش PDF، بازیابی، مسیریابی و مدیریت خطا؛
- بهبود ارزیابی و وفاداری پاسخ به متن و مستندسازی تنظیمات و نمونه‌های اجرا.

این موارد برنامه توسعه‌اند و نباید به‌عنوان قابلیت‌های کامل‌شده نسخه فعلی تلقی شوند.

## امنیت و مشارکت

### امنیت داده و کلیدها

پیش از عمومی‌کردن مخزن، مطمئن شوید هیچ‌یک از موارد زیر در Git ثبت نشده‌اند:

- کلید API؛
- فایل‌های `.env`؛
- اسناد دارای محدودیت انتشار؛
- داده‌های خصوصی؛
- پایگاه برداری محلی `chroma_db/`؛
- PDFها یا فایل‌های ورودی حساس؛
- محیط مجازی Python و سایر داده‌های محلی قابل بازسازی.

حداقل باید محیط مجازی، فایل‌های محیطی، کش Python و `chroma_db/` در `.gitignore` پوشش داده شوند. پوشه `/data` را فقط پس از بررسی مجوز و محتوای فایل‌های آن عمومی کنید.

اگر فایلی پیش‌تر commit شده باشد، افزودن آن به `.gitignore` به‌تنهایی آن را از تاریخچه Git حذف نمی‌کند. در چنین شرایطی، تاریخچه و کلیدهای در معرض خطر را به‌صورت جداگانه بررسی کنید و در صورت نیاز کلیدها را باطل و جایگزین کنید.

### مشارکت

برای مشارکت، ابتدا وضعیت مخزن و راهنمای تنظیمات را بررسی کنید؛ سپس تغییرات کوچک و مشخص را همراه با توضیح، آزمون مرتبط و به‌روزرسانی مستندات ارائه دهید.

پیش از انتشار عمومی، خروجی `git status` و محتوای فایل‌های آماده commit را بازبینی کنید:

```bash
git status
git diff --staged
```

تا زمانی که مجوزی به مخزن افزوده نشده است، مجوز استفاده یا بازتوزیع خاصی را مفروض نگیرید. همچنین پیش از استفاده یا انتشار مقاله‌ها و داده‌های ورودی، محدودیت‌های حق‌نشر و مجوز آن‌ها را بررسی کنید؛ این پروژه مجوز انتشار محتوای مقاله‌ها را ایجاد نمی‌کند.
